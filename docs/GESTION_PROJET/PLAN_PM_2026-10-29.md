## 1. Résumé exécutif

**Le backlog n'est pas bloqué par du code manquant. Il est bloqué par la capacité CI.**

| Indicateur | Valeur mesurée |
|---|---|
| Issues ouvertes | **10** |
| PR ouvertes | **9** |
| `main` | `c419ebe8f4` |
| Checks requis sur `main` | **annulés** (aucun vert, aucun rouge) |
| Runs Actions `queued` | **164** (le plus ancien : 08:55Z) |
| Runs Actions `in_progress` | 19 |
| Runners self-hosted enregistrés | **0** |
| Quota merges (`MERGE_DAILY_QUOTA`) | 80/j — **non saturé** |

Trois conséquences directes pour le pilotage :

1. **`main` n'est ni vert ni rouge : il est indéterminé.** Tous les check-runs du
   SHA de `main` ressortent `cancelled`. On ne peut donc pas affirmer « main est
   vert » — et on ne doit pas fusionner en le supposant. C'est un risque produit,
   pas une formalité.
2. **Le goulot n'est pas le quota de merges** (80/jour, très loin d'être atteint)
   mais **le débit de la file Actions**. Fusionner plus vite ne sert à rien tant
   que les checks requis ne se terminent pas.
3. **Les 9 PR ouvertes sont toutes `mergeable=True` et sans échec rouge.** Aucune
   n'a de défaut de contenu connu. Le seul obstacle est la production des checks.

**Ce qui débloque le plus de valeur en premier :** réduire le fan-out CI (lot 0),
puis fusionner les 2 PR canoniques (lot 1). Rien d'autre ne progresse avant.

## 5. Risques et dette

### R1 — Fan-out CI (risque n°1, avéré)

| Mesure | Valeur |
|---|---|
| Workflows | **89** |
| Déclenchés sur `pull_request` | **59** |
| `cancel-in-progress: false` sur un workflow PR | **9** |
| `cancel-in-progress: true` | 20 |
| `cancel-in-progress` conditionnel PR-only | 35 |
| Runs en file | 164 |

Chaque push sur une branche empile ~20 à 30 runs. Avec plusieurs agents qui
poussent en parallèle, la file ne draine jamais : **c'est la cause racine des
sessions qui tournent sans rien fusionner.** Le dépôt documente déjà le problème
(#7090) mais ne le mesure qu'une fois par mois — trop lent.

Mitigation immédiate déjà appliquée : annulation des runs dont le SHA est
dépassé (aucune information perdue, ils ne testaient plus le HEAD).

### R2 — `main` indéterminé

Aucun check requis vert sur `c419ebe8f4`. Il faut **rejouer** les 4 checks requis
sur `main` avant de déclarer quoi que ce soit « vert ». Ne pas confondre
« aucun échec » et « succès ».

### R3 — PR docs en collision (#9027 / #9032)

Même fichier, même base. Sérialiser, puis rebaser. Ne pas fusionner les deux en
l'état.

### R4 — Doublons #7962

Deux branches orphelines (`fix/7962-attendance-controller`,
`fix/7962-selfservicetrial-action`) portent le même travail que #9019. Elles
doivent être supprimées **après** merge confirmé, pas avant.

### R5 — Backlog « draft » non décomposé

#7924 est un épique `P0` dont **aucune issue fille n'existe**. Tant que la spec
n'est pas validée, l'épique reste un contenant vide : il gonfle le décompte
d'issues ouvertes sans produire de travail planifiable.

### R6 — Quota Vercel

`Deployment rate limited — retry in 24 hours` sur le tip de `main`. Tant que la
fenêtre n'est pas écoulée, aucun redéploiement front n'est vérifiable — donc
#7994 ne peut pas être **clôturée**, seulement préparée.

## 6. Décisions PM prises dans ce plan

1. **Priorité au déblocage CI plutôt qu'à l'écriture de code.** Les 9 PR sont
   sans échec connu ; produire une 10ᵉ PR n'apporte rien tant que la file ne
   draine pas. C'est un arbitrage explicite, pas une esquive.
2. **Une PR par tranche, déclarée `Part of`.** Le garde #5442 a été conçu pour
   ça : une PR qui ferme, N PR qui contribuent. On garde ce modèle.
3. **Aucune fermeture d'issue sans preuve.** Les issues `blocked` par une action
   propriétaire restent ouvertes après livraison du code : le code seul ne
   satisfait pas leurs critères d'acceptation (ex. #7967 exige le worker payant).
4. **Pas de suppression de table historique dans le lot #8727.** La séquence
   additive de l'issue est respectée à la lettre.
5. **#7941 n'est pas un travail d'ingénierie.** C'est un process humain ; il ne
   doit pas être planifié comme un lot de dev.
