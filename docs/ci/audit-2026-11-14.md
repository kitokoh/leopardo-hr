### Étape fautive

L'étape 8 « Run backend feature tests » est `success` (grâce à `continue-on-error: true`).
C'est l'étape **11 « Fail backend job if unit tests failed »** qui échoue
(`Process completed with exit code 1`).

### Cause réelle

**Un seul test unitaire échoue**, et il fait tomber tout le job :

```
FAILED  Tests\Unit\Recruitment\ResumeTextExtractorTest > it extracts text from a pdf
pdftotext doit extraire le texte d un PDF texte.
Failed asserting that null is not null.
  at tests/Unit/Recruitment/ResumeTextExtractorTest.php:124

Tests: 1 failed, 3 risky, 4 skipped, 1237 passed (7615 assertions)
```

`ShellResumeTextExtractor` (module Recruitment) appelle le binaire **`pdftotext`**
(paquet `poppler-utils`) pour extraire le texte des CV PDF. Le runner
`ubuntu-latest` **ne l'embarque pas**, et aucun workflow ni action composite ne
l'installait : `grep -n "poppler\|pdftotext\|apt-get install"` sur
`.github/workflows/tests.yml` et `.github/actions/*/action.yml` ne renvoie **rien**.

Le test est donc structurellement rouge sur `main`, indépendamment du code applicatif.

### Correctif appliqué

Installation de `poppler-utils` dans l'action composite **partagée**
`.github/actions/setup-backend-db/action.yml`, donc visible par tous les jobs backend
(tests, coverage, shards) :

```yaml
- name: Install PDF text extraction tooling (poppler-utils)
  shell: bash
  run: |
    if command -v pdftotext >/dev/null 2>&1; then
      echo "pdftotext déjà présent : $(pdftotext -v 2>&1 | head -1)"
      exit 0
    fi
    sudo apt-get update -qq
    sudo apt-get install -y -qq poppler-utils
    pdftotext -v 2>&1 | head -1
```

L'étape est **idempotente** (sortie immédiate si le binaire est déjà là), donc sans
coût sur un runner qui l'aurait déjà.

Par événement : `pull_request` 21, `push` 15, `workflow_run` 1.

### Mécanisme réel

Deux mécanismes distincts, tous deux **légitimes** :

1. **`concurrency` natif de GitHub** sur les branches de PR. `tests.yml` porte
   `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` : un nouveau push
   sur une PR annule le run précédent de la même branche. C'est le comportement voulu
   (feedback rapide), documenté en commentaire dans le workflow.

2. **`dev-hub/tools/cancel-orphan-runs.sh --superseded`**, lancé par
   `.github/workflows/cleanup-orphan-runs.yml` (cron toutes les 2 h + à la fermeture de
   PR). Il annule les runs `queued`/`in_progress` des branches mortes et les runs
   `queued` supersédés.

### Point important : `main` n'est pas annulé par le nettoyage

Le script **protège explicitement** la branche par défaut :

- `DEFAULT_BRANCH` est lu depuis l'API et injecté dans `PROTECTED_BRANCHES` ;
- `is_protected()` est consulté avant **chaque** annulation, dans les deux modes ;
- le mode `--superseded` filtre en plus `select(.head_branch != "main")` dans son `jq` ;
- une garde **fail-closed** annule tout le nettoyage si la liste des branches vivantes
  est vide (évite une annulation en masse sur une lecture API en échec).

Les 16 annulations de `main` observées s'expliquent donc autrement, et les horodatages
le montrent : elles arrivent **en grappe, 1 à 2 secondes après un push** sur `main`
(04:08:58 → 04:12:54 ; 04:12:52 → 04:13:08). Ce sont des runs **remplacés par le run du
push suivant** — le comportement normal de la file, pas un bug de protection.

### Cause profonde de la pression sur la file

Le job Backend dure **1 h 55** (mesuré ci-dessus) et la suite Feature complète
**6 043 s ≈ 1 h 41** à elle seule (`Duration: 6043.21s, Parallel: 4 processes`). Avec
des jobs de cette taille, chaque push sur `main` occupe un slot pendant près de deux
heures : les runs suivants attendent, puis sont remplacés. Le workflow documente déjà
cette dynamique (issues #6928, #9311, #9401) et a posé un plafond d'étape à 210 min
pour qu'une suite suspendue libère le groupe.

### Correctif

**Aucun correctif de code n'est nécessaire pour ce point.** Le mécanisme d'annulation
est conforme à son intention et la protection de `main` fonctionne. Le levier réel est
la **durée** des jobs, pas la politique d'annulation — et ce levier est déjà identifié
et instrumenté dans le dépôt (#6928 : fixture construite une fois par base).

| Avis | `GHSA-gcqx-w48m-w2h4` / `CVE-2026-93753` |

| Sévérité | **faible** (CVSS 5.3, EPSS 0,5 %) |
| Version installée | 4.3.1 |
| Plage vulnérable | `>= 4.2.0, <= 4.3.1` |
| **Version corrigée** | **aucune** (`first_patched_version: null`) |
| Manifeste | `front/web/package-lock.json` |
| Type | `dev: true` — outillage de test |
| Chaîne | `jest` → `jest-config` → `deepmerge ^4.3.1` |

### Pourquoi il n'y a rien à monter

`4.3.1` est la **dernière version publiée** sur npm (`dist-tags.latest = 4.3.1`,
publiée le 2023-03-16 ; les 10 dernières versions du registre s'arrêtent à 4.3.1).
L'avis lui-même déclare `first_patched_version: null`. Un bump réinstallerait donc
exactement la version vulnérable.

La dépendance est **`dev` uniquement** et n'est atteinte que par `jest-config`, donc par
`npm test` : aucun chemin d'exécution de production ne la charge. Le vecteur
(pollution de prototype dans `mergeObject()`) exige un objet source contrôlé par un
attaquant ; dans `jest-config`, les objets fusionnés sont les fichiers de configuration
Jest du dépôt, déjà versionnés et relus.

### État réel

**Déjà résolu sur `main`** par le commit `658a1424` (PR #9476, mergée le
2026-11-14 à 10:35:39Z), qui documente la décision de **risque accepté** dans
`docs/security/DEPENDABOT_ALERTES_SUIVI.md` avec exactement les faits ci-dessus.

L'alerte reste `open` côté GitHub — c'est attendu : elle ne se fermera qu'à la
publication d'une version corrigée en amont, ou par une dismissal manuelle dans
l'onglet Security. **Aucune action de code n'est possible ni utile ici.**

## 4. Suites complètes Accounting et Payroll en local

### Environnement

PostgreSQL 15 + Redis 7 locaux, base `leopardo_test` recréée proprement
(`DROP DATABASE ... WITH (FORCE)` puis `CREATE DATABASE` + extensions `postgis`,
`pg_trgm`).

Deux pièges d'environnement ont dû être neutralisés, et méritent d'être connus :

1. **`tests/TestCase.php` réécrit l'hôte en `pgsql`** quand il se croit dans Docker
   hors CI (`isRunningInsideDocker() && !$isCI` → `$host = 'pgsql'`). Dans ce sandbox,

   "pgsql"`. Contournement : `CI=true` à l'exécution.

   `relation "migrations" does not exist` puis
   `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`.
   Il faut recréer la base, pas seulement relancer.
