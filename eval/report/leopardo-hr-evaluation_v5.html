🔴 Bloquant corrigé — le tenant restaurateur n'était pas provisionnable

Trois manques cumulés rendaient le tenant inutilisable au-delà du compte principal :

  • Modules requis absents. Le manifest RestaurantManager déclare requiredModules() = rh, documents, notifications, crm. Le seeder ne posait que rh et restaurantmanager : SolutionActivator::activate() refusait la verticale et les routes /crm/* et /documents/* répondaient 403.
  • Aucun user_lookups. La table publique qui résout un email vers un tenant n'était pas alimentée : aucun des 8 profils ne pouvait se connecter.
  • Aucune assignation de ressource. L'autorisation Restaurant est ressource-scopée sur restaurant_branch via canWriteBranchResource(). Sans assignation, la méthode retombe sur le comportement historique (principal/rh seulement) : un caissier ne pouvait pas ouvrir sa caisse, un chef ne pouvait pas piloter la cuisine, un serveur ne pouvait pas encaisser — tous en 403.

Correction : RestaurantUatSeeder pose les 6 features, les 8 user_lookups, les assignations par métier (manage pour direction/comptable/superviseur/chef, operate pour serveur/caissier, view pour livreur) et l'ensemble des données RH/CRM/documents.

6 · Bugs et correctifs

🔴 1 — GET /restaurant/tables renvoyait 500

Le seeder insérait status = 'available' dans restaurant_tables, alors que l'enum RestaurantRecordStatus n'accepte que active|disabled. La sérialisation de la ressource levait une ValueError → 500 pour tous les profils.

Correction : 'status' => 'active' dans RestaurantUatSeeder.

🔴 2 — GET /restaurant/orders renvoyait 500

Même cause sur restaurant_order_items.status = 'served' : l'enum OrderItemStatus n'accepte que active|cancelled. Toute lecture de la liste des commandes échouait.

Correction : 'status' => 'active'.

🔴 3 — GET /expense/stats : 403 pour tout le monde, puis 500

Deux bugs enchaînés sur le même endpoint :

  • Les Gates expense.reports et expense.manage appelées par ExpenseStatsController n'étaient définies nulle part : cannot() renvoyait toujours vrai, donc 403 pour tous les profils, y compris le principal et le comptable. C'est exactement le même trou que #9680 (recruitment.view), déjà documenté dans le code.
  • Une fois la Gate franchie, la requête de répartition par catégorie s'exécutait sur une colonne category absente du schéma expense_claims → SQLSTATE 42703 → 500. Le commentaire annonçait « si la colonne existe, sinon on saute » mais aucune vérification n'était faite.

Correction : Gates branchées sur ExpenseClaimPolicy + garde Schema::hasColumn(). Vérifié : principal / comptable / gérant / serveur → 200.

🟠 4 — pilot:seed resto --clean ne permettait pas de re-seeder

La purge supprimait les employés et l'entreprise mais pas public.user_lookups, qui porte un index UNIQUE sur email. Un --clean suivi d'un re-seed échouait donc en violation d'unicité — le cycle de recette était impossible à rejouer.

Correction : PilotSeedCommand purge aussi public.user_lookups par company_id.

🟡 Manques constatés — état après la v3

  • ✅ Corrigé (v3) — Bridge d'impression non documenté. GET /restaurant/printing/bridge/health renvoie 403 pour les 8 profils, y compris le principal : la route attend un jeton d'appareil (X-Restaurant-Print-Bridge-Token + X-Company-Id), hors Sanctum. Comportement voulu, mais l'OpenAPI ne l'expliquait pas — la spec décrit désormais le mécanisme, l'authentification dédiée et le fail-closed.
  • ✅ Corrigé (v3) — GET /restaurant/print-jobs : paramètre non documenté. Le code lit branch_id en query (422 sans lui) alors que la spec déclarait un en-tête X-Branch-Id qui n'existe pas. La spec documente maintenant branch_id (obligatoire) ainsi que les filtres status et order_id.
  • ✅ Corrigé (v3) — Anomalie RBAC sur POST /departments. La route ne portait qu'un api.manager sans liste de rôles : comptable et superviseur obtenaient 201. Elle est désormais restreinte à principal et rh, et DepartmentController::store() évalue enfin DepartmentPolicy::create() (défense en profondeur).
  • Routes de statistiques non homogènes : /employees/stats, /documents, /crm/activities, /planning → 404 alors que des équivalents existent ailleurs.
  • Payloads de verticales très stricts et non documentés : restaurant/products exige code + category_id + price_minor ; restaurant/orders exige order_type et table_id pour dine_in. Messages de validation clairs et localisés, mais l'OpenAPI gagnerait à exposer ces schémas exacts.
  • Contacts CRM chiffrés : les colonnes email/phone de crm_contacts sont castées encrypted — le seeder doit passer par le modèle Eloquent, une insertion SQL brute produit des valeurs illisibles. À documenter pour les intégrateurs.

Verdict

Produit mature et cohérent. Le point faible n'est pas le code métier mais le provisionnement : un tenant de verticale n'était pas livrable en l'état (modules requis, comptes de connexion, assignations de ressource). C'est corrigé en v2, et le cycle --clean + re-seed est désormais rejouable. La v3 a fermé les trois points RBAC/OpenAPI. La v4 ferme les trois derniers points ouverts : les routes de statistiques répondent désormais de façon homogène, les payloads de la verticale restaurant sont documentés dans l'OpenAPI, et le bridge d'impression est couvert par un test de bout en bout. Aucun point ouvert de la recette ne reste sans réponse.
