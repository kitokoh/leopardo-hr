Le renderer d'exceptions HTTP préserve désormais les headers du throttling (`Retry-After`/`X-RateLimit-*`). Tests : panne du stockage → 429 + Retry-After (au lieu de 500), `/health` OK pendant la panne, dépassement nominal → 429 + Retry-After.
- **fix(api): rate limiter — `$next()` hors try sur le chemin `Limit::none` (suivi #1774).** Deux défauts constatés en review post-merge de `ResilientThrottleRequests` : sur les routes non throttlées (`/health`, limiters `Limit::none`), une exception du pipeline en aval (contrôleur) était attrapée par le `catch (\Throwable)` du middleware et convertie en 429 dégradé — masquant l'erreur réelle et contredisant le contrat documenté (« `$next()` s'exécute HORS du try/catch ») ; le docblock de `RateLimiterResilienceTest` référençait par ailleurs `App\Support\Cache\ResilientRateLimiter` (inexistant). Comportement nominal inchangé : dépassement → 429 + Retry-After, panne du stockage → 429 dégradé + `report()`, headers `X-RateLimit-*` préservés.
